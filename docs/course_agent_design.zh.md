# 课程 Agent 设计

课程设置不再要求教师先填完一张大表。教师可以先描述教学目标，Agent 只追问当前缺少的最小信息，然后把计划、调用步骤和可修改草稿展示出来。

## 一次课程设计的流程

1. 在「课程与学习进展」的「协作式课程设计」中，用自然语言描述学员要练什么。可以同时说明案例数量、难度和风险，例如：

   > 我想让初学者练习情绪验证，做 3 个低风险案例。

2. Agent 解析出目标和约束。目标或案例数量缺失时，它只提出对应问题，不启动检索或生成。
3. 信息足够后，界面显示课程主题、案例数量、难度、风险，以及下一步会调用的工作：课程蓝图、知识检索和情景批量生成。
4. 教师点击「确认并生成课程草案」后，已有的课程蓝图服务检索适用知识，生成目标、可观察行为、知识卡和微练习。这个阶段只产生可编辑草稿，不保存正式课程，也不自动生成病例。
5. 教师可以继续通过对话补充约束，也可以展开「高级编辑」逐项修改。确认目标和知识卡后，再生成病例草案；审核并选择案例后，才保存并分配课程。

## 为什么这样设计

课程目标、知识依据、微练习和病例之间存在依赖关系。先展示计划再执行，可以让教师看到 Agent 将要做什么，避免一次模型调用默默决定所有设置。草稿与正式课程分开，也使修改和回退成本更低。

## Agent、Skill 和 Task 的边界

- 课程 Agent 负责收集意图、整理约束、提出问题和编排下一步。
- `course_blueprint` 负责根据教学目标和知识范围生成可编辑课程起点。
- `knowledge_retrieval` 负责为课程目标选择适用的知识范围；风险识别、回应审阅等其他功能使用各自的检索策略。
- `scenario_batch_generation` 负责在课程目标确认后生成情景批次。
- Task 记录一次生成、审阅或批量任务的进度；课程 Agent 不会把每条聊天消息都创建成 Task。

当前课程 Agent 的意图解析是本地确定性的，模型不是必需依赖。这样可以在本地模型能力有限时仍保持可预测的确认门；知识解释和课程内容仍由已有模型配置和检索流程完成。

## 当前边界

课程 Agent 目前收集课程目标、模板、案例数量、难度和风险，并把这些参数传给现有课程蓝图流程。目标、知识卡和微练习的细节修改仍通过高级编辑完成；下一步可以把常用的“增加一个练习”“把目标改成可观察行为”等编辑操作注册为受控工具，让对话直接生成结构化补丁，再由教师确认。

## 验证方式

后端单元测试覆盖缺少信息、确认计划、中英文输入和默认值；浏览器回归测试验证了“发送描述 → 显示计划 → 未确认前不调用蓝图 → 确认后生成草稿”的完整路径。测试使用合成接口响应，不调用真实模型。
